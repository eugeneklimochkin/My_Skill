# Протокол benchmark

## 1. Когда нужен benchmark

Использовать этот режим для сравнения:

- разных языковых моделей;
- разных версий одной модели;
- системных промптов и навыков;
- глубины рассуждения и доступного набора инструментов;
- качества до и после изменения KLS или предметного модуля.

Обычная финальная приемка одного рабочего документа не требует создания отдельного тестового корпуса.

## 2. Единица benchmark

Каждое задание состоит из:

1. task.json с коротким поручением, результатами и рубрикой;
2. каталога materials с обезличенными, синтетическими или разрешенными материалами;
3. закрытой рабочей среды;
4. каталога output только для конечных результатов;
5. записи траектории, охвата документов, времени, стоимости и версии конфигурации.

Материалы должны отражать реальную сложность: значимые документы, дубли, противоречия, устаревшие версии и разумные отвлекающие материалы.

## 3. Схема задания

Минимальный task.json:

    {
      "task_id": "litigation/draft-statement-of-claim/scenario-01",
      "title": "Иск о взыскании долга и неустойки",
      "jurisdiction": "Российская Федерация, арбитражный процесс",
      "legal_date": "2026-08-26",
      "work_type": "draft",
      "instructions": "Подготовить иск от имени покупателя и расчет требований.",
      "deliverables": {
        "claim.docx": "Исковое заявление",
        "calculation.xlsx": "Расчет требований"
      },
      "criteria": [
        {
          "id": "C-001",
          "title": "Верно определено начало просрочки",
          "match_criteria": "PASS, если дата начала просрочки рассчитана от договорного срока оплаты с учетом подтвержденной даты приемки. FAIL в остальных случаях.",
          "priority": "blocking",
          "deliverables": ["claim.docx", "calculation.xlsx"],
          "sources": ["contract.pdf", "acceptance-act.pdf"]
        }
      ]
    }

Поля Harvey LAB сохранены для совместимости. Российские расширения: jurisdiction, legal_date и priority.

## 4. Проектирование поручения

Поручение должно:

- звучать как реальная постановка старшего юриста;
- называть сторону, цель и требуемые результаты;
- не перечислять все скрытые проблемы;
- содержать достаточно данных для выполнения либо прямо разрешать список вопросов;
- не подсказывать критерии и не раскрывать ожидаемые выводы;
- определять дату, на которую проверяется право.

Не оценивать общую эрудицию вне материалов, если задача предполагает закрытый комплект. Для исследования права отдельно определить доступ к внешним источникам.

## 5. Проектирование материалов

Для каждого сценария проверить:

- все необходимые факты действительно содержатся в материалах;
- каждый критерий имеет один или несколько названных источников;
- нет случайного отсутствия документа, делающего задачу нерешаемой;
- противоречия являются осознанными и оцениваются рубрикой;
- отвлекающие материалы реалистичны;
- персональные данные, коммерческая тайна и адвокатская тайна обезличены либо использование прямо разрешено;
- сканы, таблицы, подписи, ЭДО и приложения доступны в том виде, который должен обработать испытуемый.

Не считать синтетический документ автоматически безошибочным. Перед включением его проверяет юрист.

## 6. Проектирование критериев

Каждый критерий:

- атомарен;
- оценивается бинарно;
- содержит прямое условие pass и fail;
- проверяет конечный результат, а не скрытые действия;
- связан с конкретными результатами;
- называет источники, если проверяется факт из материалов;
- проверяет смысл, а не ключевое слово;
- имеет только один приоритет.

Не использовать весовые коэффициенты для компенсации материальной ошибки. Не включать критерии «хорошо написано» без конкретного наблюдаемого стандарта.

## 7. Сопоставимые условия запуска

Перед сравнением заморозить:

- версию задания и хеш материалов;
- системный промпт и набор навыков;
- модель, версию, температуру и глубину рассуждения;
- доступные инструменты и сетевой доступ;
- лимит ходов, токенов и времени;
- юридически значимую дату;
- состав оценщиков и их настройки.

Одинаковое имя модели не гарантирует одинаковую конфигурацию. Каждую конфигурацию записывать полностью.

## 8. Оценка

Для каждого критерия оценщик получает:

- название задания;
- только относящиеся к критерию конечные результаты;
- название критерия;
- условие match_criteria;
- названные источники, когда для решения требуется сверка материалов.

Оценщик возвращает status и краткое обоснование. Температура оценки должна быть нулевой или минимально доступной.

Для значимого сравнительного исследования предпочтительны два независимых оценщика. Они оценивают каждый критерий отдельно. Разногласие не скрывается средним значением: спорный критерий рассматривается юристом по источникам.

## 9. Показатели

Основной показатель:

- all-pass rate: доля запусков, в которых пройдены все применимые blocking и required критерии.

Диагностические показатели:

- criterion pass rate;
- число и категории непрохождений;
- доля прочитанных материалов;
- доля непроверенных источников;
- число исправительных циклов;
- время;
- токены и стоимость;
- стабильность повторных запусков;
- согласие оценщиков.

Не ранжировать модели только по criterion pass rate. Результат с 99 процентами и одной критической ошибкой не готов.

## 10. Повторяемость

Для каждой конфигурации выполнять несколько запусков на разных сценариях. Не делать вывод о превосходстве по одному заданию.

Минимальный отчет указывает:

- число заданий и запусков;
- распределение по практикам и типам работы;
- all-pass rate с числителем и знаменателем;
- диагностический процент критериев;
- критические категории ошибок;
- условия и дату запуска;
- ограничения выборки.

## 11. Запись оценки для скрипта

Скрипт score_rubric.py принимает:

    {
      "task_id": "example-01",
      "criteria": [
        {
          "id": "RF-F01",
          "title": "Нет выдуманных фактов",
          "priority": "blocking",
          "verdict": "pass",
          "reason": "Все материальные факты сверены.",
          "source": "contract.pdf, pages 2-4"
        }
      ]
    }

Допустимые priority: blocking, required, additional. Допустимые verdict: pass, fail, na, unverified. Для fail, na и unverified причина обязательна.

## 12. Защита от утечки

- Не включать рубрику в поручение испытуемому.
- Не использовать один и тот же конфиденциальный материал вне разрешенного контура.
- Не смешивать обучающие примеры с закрытым тестом.
- Не менять материалы или критерии между сравниваемыми запусками.
- Изменение рубрики создает новую версию задания и требует повторной оценки всех сравниваемых результатов.
